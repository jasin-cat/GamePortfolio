作品概要

姿を変えながら進むランアクションゲームです。チーム（計7名）で約3ヶ月かけて制作し、私はプレイヤーの操作・状態管理と、ゲーム進行・演出を担当しました。

使用技術

Unity / C# / UniTask / UniRx / NaughtyAttributes / DOTween / State Pattern / Rigidbody2D

担当内容

  • プレイヤーの状態切り替え・入力・物理挙動
  • ゲーム進行・スコア・マップ移動の制御
  • ポーズ、音声・アニメーション・フェード演出

技術解説

  • State Patternで操作ごとの処理を分離し、終了時に重力や回転を復元。
  • Updateで入力を受け、FixedUpdateで物理挙動を更新。
  • UniRxで状態変更を通知し、DOTween・UniTaskで演出とフェードを制御。

設計の工夫と選択理由

「何を選んだか」と「なぜ選んだか」、比較した方法をまとめています。

設計要素 採用した方法 ねらい 比較した方法・避けた理由
プレイヤー操作の切り替え State Pattern（共通のIState） 操作ごとの処理をクラスに分離し、状態を抜けるときに重力・回転を元に戻せるようにする 1つのクラス内のif・switch分岐 → 操作を追加するたびに分岐が増え、コードの可読性が損なわれるため
入力と物理挙動 Updateで入力、FixedUpdateで速度変更 入力の取りこぼしを防ぎつつ、物理挙動を一定間隔で安定して更新する Updateで直接速度を変更 → フレームレートによって移動量やジャンプの高さが変わってしまうため
状態変更の通知 UniRx 状態の変化を購読側へ通知し、進行管理と演出を疎結合にする 各クラスから直接メソッドを呼ぶ → クラス同士が密結合になり、変更の影響が広がるため
フェード・シーン遷移 DOTween、UniTask フェード完了を待ってから処理を実行し、処理中はUIへの入力を遮断する コルーチンの入れ子 → 待ち処理の流れが追いにくいため

苦労した点と解決方法

「現象 → 原因 → 対策」の順で、開発中に直面した課題をまとめています。

課題1：状態を切り替えても、前の状態の動きが残ってしまう

現象 重力反転などの状態から別の状態に切り替えたあとも、重力の向き・縦方向の速度・キャラクターの向きが前の状態のまま残り、意図しない動きになった。
原因 各状態が変更したRigidbody2Dの重力・速度や回転を、状態を抜けるときに元に戻す処理がなかった。
対策 各状態の Exit() で、変更した重力・縦方向の速度・回転を初期値に戻すようにした。状態の切り替えでは必ず Exit() → Enter() の順に呼ぶため、どの状態から切り替えても同じ初期状態から始まり、状態を追加しても影響が出にくくなった。

課題2：マップと背景の切り替えタイミングがずれる

現象 マップは横にスクロールしながら切り替わるのに、背景は一瞬で切り替わるため、マップと背景の見た目がずれていた。
原因 マップが切り替わり始めた瞬間に、背景のスプライトをすぐに入れ替えていた。
対策 マップの切り替えと同時に背景をクロスフェードさせ、徐々に切り替えることで、ズレを目立ちにくくした。ただし完全には一致していないため、今後の改善点としている。

既知の課題と今後の改善予定

既知の課題

  • マップが切り替わってから数秒後にプレイヤーの状態を切り替える仕様のため、マップのスクロール速度が上がると、マップは切り替わったのにプレイヤーの状態が前のままになってしまう。

次に改善したい点と、その理由

  • マップの進むスピードに合わせて、状態を切り替えるまでの待ち時間を調整する。
